# クイックスタート

AstroForgeはローカルで起動し、ブラウザで機体を組み立て、外部プログラムからUDPで操縦します。外部アカウントやAPIキーは不要です。

## インストールと起動

[Node.js](https://nodejs.org/) 22.12以降、[Zig](https://ziglang.org/download/) **0.16.0**、Gitを用意します。現在はソースから起動するため、利用する場合も初回の物理エンジンのビルドにZigが必要です。Pythonサンプルを使う場合だけPython 3も用意してください。

```sh
git clone https://github.com/Ampoi/AstroForge.git
cd AstroForge
node --version
zig version # 0.16.0
npm ci
npm start # 型チェック・物理Wasm・UI・ドキュメントのビルド後に起動
```

シミュレーターは `http://localhost:3000/`、ドキュメントは `http://localhost:3000/docs/` で開けます。起動したターミナルは開いたままにしてください。サーバーを終了するには、そのターミナルでCtrl+Cを押します。

ブラウザで表示・組み立てを行い、点火・姿勢制御はUDPコントローラーから行います。「発射台へ」は機体を配置する操作で、自動点火はしません。

## 最初のフライト

起動直後はフライト画面です。保存機体のない初回起動では、2段機体のPathfinder 02 / Two stageが発射台に配置されています。保存済みの機体がある場合は、最後に保存した機体を使用します。

```sh
# 別のターミナルで、同じAstroForgeフォルダに移動して実行
npm run demo
```

コマンドを実行すると、デモがUDPテレメトリを読み、制御権を取得して自動点火します。起動直後は「発射台へ」の操作は不要です。第1段の燃料が尽きると分離リングで下段を切り離し、分離をテレメトリで確認して0.8秒後に第2段を点火します。予測遠地点160 kmで推力を停止し、4分で制御権を返します。段ごとの点火・分離はターミナルに記録されます。2段プリセットは上段にも安定翼を備え、高度30 kmまでは垂直に上昇します。×2・×5・×10では、制御周期に合わせて姿勢補正を調整します。Ctrl+Cで推力を切り、制御権を返します。

## 機体を選ぶ・作る

「機体」メニュー →「保存機体・プリセットを選ぶ」から、1段・2段プリセットや保存した機体を選択できます。「発射台へ」で配置、「VABで編集」で組立室を開きます。保存機体からステージングのデモへ切り替える場合は2段プリセットを配置し、機体一覧でUDPをONにして「接続コマンド」を実行してください。

「新しい機体を作る」は空のVABを開きます。最初にポッドや燃料タンクなどの胴体パーツを配置すると、機体のルート（◆）になります。パレットでパーツを選び、作業場をクリックするかドラッグして配置してください。空いている断面を近づけて重ねると中心へスナップします。マウスが断面を直接指していなくても、断面同士の重なりと軸方向の距離で判定します。使用済みの面や移動中の子パーツには接続しません。AltキーまたはスナップOFFで自由配置できます。

接続面の縁は **標準径 ⌀1.25 m が緑**、**細径 ⌀0.40 m が紫**、**矩形などが橙** です。細径は直動モーターの外径を0.40 mへ揃え、コマンドポッドの小さい上端にも適用しています。パーツ選択時に上下の接続寸法を表示します。異なる規格同士も接続でき、スナップ時の案内に「異径接続OK」と表示します。新しいパーツ種別は追加していません。

配置済みパーツは子パーツごとドラッグできます。ルートから外すとそのパーツ群は半透明になり、未接続のまま置いておけます。未接続パーツはパーツ数・質量・TWR・Δv・保存・発射に含まれず、再接続すると子パーツもまとめて復帰します。ルートを移動すると機体全体が動きます。Escで取消、⌘Zで元に戻せます。

「保存」は接続済みの機体を保存し、「発射台へ」はその機体を配置します。未接続パーツを含む作業状態はブラウザの下書きに保持されます。「フライトへ戻る」は現在の飛行を継続します。飛行中にVABを開いても既存の機体は計算され続けます。

発射台上の未発射機体は新しい機体に置き換わります。飛行中の機体は維持されますが、発射台付近に機体がある間は追加配置できません。

## カメラと制御対象

「機体」メニューの「追尾」はカメラだけを変更します。分離した段や破片も追尾できます。画面の背景にフォーカスがあるときはTabで順送りできます。ボタンなどの操作中は通常のキーボード移動を優先します。

機体ごとの「UDP ON/OFF」で外部制御を切り替えます。複数機体を同時にONにでき、一覧に専用のコマンド受信・テレメトリ送信ポートが表示されます。「接続コマンド」をコピーし、機体ごとに別のターミナルでデモを起動できます。初期機体はON、追加配置した機体はOFFです。

OFFにするとその機体の指令とleaseを解除し、UDP送受信を停止します。再ONでは同じポートを使って新しいセッションを発行するため、コントローラーを再接続してください。他の機体のセッションは維持します。分離物は追尾のみ可能です。

## 時間と表示

画面右下の歯車（表示設定）から描画フレームレートを選べます。既定の「画面に合わせる」はディスプレイの更新に同期し、120 Hz・144 Hzなどの画面にも対応します。負荷を抑える場合は30 / 60 / 120 FPSの上限を選んでください。実測FPSも表示され、設定は同じブラウザに保存されます。実際のFPSは画面のリフレッシュレート・ブラウザ・GPUの処理能力によって変わります。

飛行中の位置と姿勢は受信した状態の間を補間して描画するため、表示は通常約0.1秒遅れます。物理計算・UDP指令・テレメトリの周期は描画設定に影響されません。バックグラウンドでは3D描画を停止します。

右上のGMTはブラウザの実際のUTC時刻です。倍率を上げてもGMTは実時間で進みます。フライト画面の数値計器は高度とGMTだけです。

×1 / ×2 / ×5 / ×10 / ×20 / ×50 / ×100 / ×200でシミュレーション速度を変更できます。物理時刻は加速しますが、UDP期限・テレメトリ周期は実時間です。20倍以上は危険な高速モードとしてオレンジ色と⚠で表示します。観測の間に大きく進むため、操縦が不安定になる場合があります。詳細は[シミュレーション仕様](./simulation)を参照してください。

## 地球と軌道の表示

飛行中は実際の慣性位置と地球自転を使い、地球の曲率、大気の縁、海・陸・極域、雲、昼夜、太陽と星空を描画します。Mキーでマップと機体追尾を切り替えられます（入力中・ダイアログ表示中を除く）。夜側でも機体の形を読み取れるよう、描画専用の弱い補助光を加えています。マップは追跡中の機体を中心に拡大・縮小し、機体の移動や追跡対象の切り替えに追従します。マップの光点は機体、オレンジの実線は実際の飛行履歴、水色の破線は現在の慣性位置・速度から求めた二体問題の予測軌道です。予測は推力と空力を無視し、地表に衝突する場合は衝突点まで、周回する場合は一周分を表示します。脱出軌道や非常に大きな楕円軌道は地心距離40地球半径までに制限します（機体がさらに遠い場合はその位置の先まで延長）。地球の裏に回った機体は隠れます。追尾カメラでも高度に応じて空が暗くなり、宇宙へ連続的に移行します。発電の昼夜判定と描画で太陽方向を共有しています。

海岸線は同梱のNatural Earth 110mデータ（約96 KB）、地表の色と雲・星は手続き生成です。描画には球面との交差計算と6サンプルの大気シェーダーを使用し、巨大な地形メッシュや外部の画像配信は不要です。大気散乱・雲・地表色は見た目の近似で、気象シミュレーションや衛星画像ではありません。地形の高低差・雲の空力影響はありません。


## 自分のプログラムから操縦する

クライアントがコマンドを**送る先**は既定で `127.0.0.1:49011`、テレメトリを**受け取るためにbindする先**は `127.0.0.1:49010` です。いずれもUDPで、1パケットに1つのUTF-8 JSONを入れます。詳細は[接続と通信の流れ](./protocol) → [送るコマンド](./udp/commands) → [受け取るテレメトリ](./udp/telemetry)の順に読めます。

付属クライアントはNode.js（TypeScript版）とPython 3版があります。Python版は標準ライブラリだけで動作します。デモ同士や自作クライアントを同じ受信ポートで同時起動しないでください。

```sh
# Node.js版：20秒で制御を終了
npm run demo -- --duration 20

# Python版：姿勢制御と推力指令のサンプル（自動分離はしません）
npm run demo:python -- --duration 90 --turn 12
```

## 起動設定

| 環境変数 | 既定値 | 用途 |
| --- | --- | --- |
| `PORT` | `3000` | ブラウザとHTTP APIのポート |
| `UDP_COMMAND_PORT` | `49011` | AstroForgeがコマンドを受け取る開始ポート |
| `UDP_TELEMETRY_PORT` | `49010` | クライアントへテレメトリを送る開始ポート |
| `UDP_TELEMETRY_HOST` | `127.0.0.1` | テレメトリの送信先アドレス |
| `ASTROFORGE_DATA_DIR` | リポジトリの `data/` | 保存機体の格納先 |
| `ZIG` | `zig` | 初回ビルドに使うZig実行ファイルのパス |

macOS / Linuxのターミナルでポートを変更する例です。

```sh
PORT=3001 UDP_COMMAND_PORT=49111 UDP_TELEMETRY_PORT=49110 npm start
# 別ターミナルから、機体一覧で実際のポートを確認して実行
npm run demo -- --command-port 49111 --telemetry-port 49110
```

コマンド用とテレメトリ用には異なるポートを指定します。機体ごとの割り当ては機体一覧で確認してください。HTTPとコマンド受信は `127.0.0.1` に固定されており、`UDP_TELEMETRY_HOST`を変えても外部からのコマンド受信は有効になりません。

## うまく動かないとき

| 症状 | 確認すること |
| --- | --- |
| 起動時にZigが見つからない・バージョンが違う | `zig version`が0.16.0か確認し、必要なら `ZIG=/path/to/zig npm start` を実行 |
| ブラウザが開けない・HTTPの `EADDRINUSE` | 起動ログを確認。既存のサーバーを終了するか `PORT` を変更 |
| デモが受信待ちのまま | 対象機体がUDP ONか、一覧の「接続コマンド」とポートが一致するか確認 |
| クライアントのbindに失敗 | 同じテレメトリ受信ポートを使うデモや受信スクリプトを終了 |
| 機体を配置しても点火しない | 追加配置した機体はUDP OFF。ONにして、その機体の接続コマンドを実行 |
| UDPを再ONにした後に指令が拒否される | セッションが変わるのでコントローラーを再起動。自作の場合は新しいheartbeatから再接続 |
| 指令を送っても動かない | [応答のreason](./udp/commands#指令の結果とエラー)と[エンジン状態](./udp/telemetry#アクチュエータ)を確認。制御権・期限・電力・燃料も確認 |

本体を改修する場合の起動・ビルド手順は[貢献](./contributing)にまとめています。
