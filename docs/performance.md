# 性能改善の実装と計測

## 実装範囲

- **排気**: `native/exhaust.zig` に粒子生成・移動・混合・地面／カプセル接触を移植。最大2,400粒子・80噴射源・80障害物を固定Wasmメモリに保持し、境界ボックスで接触候補を絞ります。障害物の軸・長さはフレームごとに一度計算します。f64 / ReleaseSafeを使用し、JS版 `ExhaustFlow` は比較用・読み込み失敗時の代替として残します。
- **排気の描画準備**: Wasmの粒子配列を直接参照し、再利用する深度配列・インデックス配列でソートします。シミュレーションの粒子順序は変更しません。GPUには生存粒子の範囲だけを転送します。透明な煙の描画方式・見た目のパラメータは維持しています。
- **物理**: 配置・乾燥慣性・単位質量あたり係数を構成ごとにキャッシュ。燃料と一液式推進剤の寄与だけ更新します。翼データは機体ごとのWasmメモリに保持し、積分の出力配列を再利用します。リセット・分離・破損後の構成は新しいキャッシュを使います。
- **状態生成・通信**: 1回の状態収集内で各機体・破片のsnapshotを再利用します。UIは `/api/events?compact=1` を使い、固定構成を `configuration` イベント、通常の状態を `data` イベントとして受け取ります。構成変更・再接続時に固定情報を再送し、リビジョンを照合して復元します。HTTPの全状態取得、従来SSE、公開UDPプロトコルは互換を保ちます。
- **機体描画**: 同一パーツ・同一親・同一材質の固定メッシュを結合。パーツ選択の境界、ジンバル、操舵、タイヤ、サスペンションの可動階層を維持します。通常描画とシャドウ描画の呼び出しが減ります。三角形数や形状は削減していません。

雲・大気のアルゴリズムはこの変更の対象外です。距離による機体LODや透明煙のオーバードロー削減は今後の候補です。

## 再現方法

```sh
npm run build:physics
npm test
npm run benchmark:physics
node --import tsx scripts/benchmark-performance.ts
npm run dev
# ブラウザーで /tests/performance.html を開き Run CPU / GPU benchmark を実行
```

ブラウザー検証ページは960×540、DPR 1、12ウォームアップ＋30測定フレームです。13パーツ、80パーツ、13パーツ×12機の噴射中のシーンを比較します。排気更新＋描画データ準備のCPU時間と、WebGL描画のGPU時間を別々に測ります。GPUタイマー拡張がなければGPU値は `null` とし、CPU時間をGPU時間として表示しません。雲・大気は除外し、機体・影・排気を描画します。JSケースも新しい深度ソートとバッファ更新を使うため、アプリ全体の変更前後比較ではなく、排気カーネルとメッシュ結合の比較です。

`benchmark-performance.ts` は7バッチの中央値を表示するCPU限定の計測です。排気は2噴射源・約2,338粒子・60 Hz、質量特性は燃料量固定、多数機体のWorld更新は互いに離した高度30 kmの12機です。通信バイト数は空のUDP付加情報・軌跡・ライブラリ1件の合成状態です。実際の通信量は軌跡長などによって変わります。

## 計測記録（2026-09-25）

Linux / Node v26.1.0 / Zig 0.16.0。同じ端末での参考値であり、速度を保証するテストではありません。

物理＋20 Hzテレメトリ生成、10秒分、5プロセスの中央値:

| 構成 | 変更前 Zig | 変更後 Zig | 比率 |
| --- | ---: | ---: | ---: |
| 13パーツ | 25.4 ms | 17.2 ms | 1.48倍 |
| 80パーツ | 77.0 ms | 18.1 ms | 4.25倍 |

排気CPU計算（描画準備・GPU描画は含まない）:

| 障害物数 | JS参照版 | Wasm | 比率 |
| --- | ---: | ---: | ---: |
| 13 | 1.0731 ms | 0.4383 ms | 2.45倍 |
| 80 | 3.3197 ms | 0.5022 ms | 6.61倍 |

質量計算は13パーツで0.0041→0.0006 ms、80パーツで0.0193→0.0007 msでした。12機体の合成状態では通常フレームが38,109→17,420 bytes（約54%減）になりました。構成変更時には別途18,782 bytesを送ります。12機のWorld更新は1ステップ0.072 msでした。

ブラウザーでの排気更新＋描画データ準備のCPU中央値と、`renderer.info.render.calls` の値（通常描画のみ。GPUタイマーの対象には影のパスも含む）:

| 構成 | JS CPU | Wasm CPU | 描画呼び出し（結合前→後） |
| --- | ---: | ---: | ---: |
| 13パーツ×1機 | 0.7 ms | 0.6 ms | 80→46 |
| 80パーツ×1機 | 3.5 ms | 0.8 ms | 812→239 |
| 13パーツ×12機 | 8.6 ms | 6.4 ms | 949→541 |

この80パーツ描画ケースは固定メッシュの多いバッテリーを追加した構成です。物理ベンチマークの80パーツは安定翼を追加した別の構成です。メッシュ結合でカリングの単位も変わるため、画面内の三角形カウンターはわずかに変わる場合があります。

ブラウザーで起動画面・排気描画・エラーの有無を確認しました。この検証ブラウザーはGPUタイマー拡張を提供しなかったため、GPU時間とFPS改善率は未計測です。

## 検証の境界

質量計算は非対称燃料・推進剤量で従来の直接集計と比較します。排気はJSとの数値比較に加え、真空での軌道速度、描画周期、地面・船体接触、停止・時間リセット・加速・容量制限・インスタンス間独立性を確認します。描画は結合前後の三角形数と境界、可動階層、粒子ソートがシミュレーション順序を変更しないことを確認します。SSEは構成変更・分離・削除・再接続・HTTPでの実ストリーム受信、配布WasmのMIMEと内容を検証します。
